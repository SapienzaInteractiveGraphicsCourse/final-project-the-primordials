\vspace{4pt}
\noindent\textbf{Abstract.} \textsc{Primordia} is a real-time laboratory for \emph{emergence}: thousands of
particles obey two simple force laws acting at deliberately different spatial scales, and the structures
that follow --- cells, filaments, worms, spirals, orbiting discs --- are never programmed explicitly. The
user does not build them; the user edits the rules, then watches, perturbs and swims through whatever the
rules produce. This document is both a technical presentation and a user manual: Sections
\ref{sec:environment}--\ref{sec:technical} cover the environment, the external dependencies and every
technical aspect of the implementation, Section \ref{sec:interactions} documents the implemented
interactions, and Section \ref{sec:manual} can be read on its own by someone who only wants to run the
application.

%=============================================================================
\section{Introduction}
%=============================================================================

The simulation superimposes two force laws, which is the conceptual core of the project.

\begin{itemize}[leftmargin=1.3em,itemsep=1pt,topsep=2pt]
  \item \textbf{Short-range ``chemistry''.} Every particle carries a discrete \emph{type} (a colour). An
        \emph{asymmetric} matrix $A$ specifies how strongly type $i$ is attracted to or repelled by type
        $j$ within a small radius $r_{\max}$. Because $A_{ij}\neq A_{ji}$ in general the system is
        non-conservative, which produces the chasing and self-propelling behaviour characteristic of
        \emph{particle life}. This term builds local structure: cells, membranes, filaments, worms.
  \item \textbf{Long-range gravity.} Every particle also carries a mass derived from its radius and
        attracts every other particle with a softened inverse-square law. This term builds global
        structure: collapse, clumping, orbits, spiral arms.
\end{itemize}

Neither force alone is novel; their superposition is what makes the application worth exploring. Gravity
assembles the coarse skeleton, chemistry decorates it, and the two fight each other in ways that are hard
to predict from the parameter values. Naive evaluation of both laws costs $O(N^2)$ per frame, far too slow
for the $1000$--$3000$ particles we target at 60\,Hz, so each law is paired with the acceleration structure
that suits its scale: a uniform grid for the short-range term, a Barnes--Hut octree for the long-range one.
Finally, the soup is inhabited: a hierarchical self-animated creature (the \emph{Grazer}) with four
articulated legs is piloted by the user, is a solid obstacle particles bounce off, and emits its own force
field --- a physical participant, not a decorative overlay.

\paragraph{Design goals.} (i) \textbf{Everything procedural} --- no mesh, image or animation files; every
vertex, texel and joint angle is computed in JavaScript at run time. (ii) \textbf{Real-time at meaningful
$N$}, which rules out all-pairs evaluation. (iii) \textbf{Everything live} --- no parameter change ever
requires a reload; particle count, type count, world size and the rule matrix are all edited while the
simulation runs. (iv) \textbf{The rules are visible} --- the octree subdivision, the gravitational field
and a deforming lattice of space can all be displayed; the acceleration structure is part of the exhibit
rather than hidden behind it. (v) \textbf{Zero-friction deployment} --- opening \file{index.html} from
disk must be enough: no build step, no bundler, no server, no \code{npm install}.

%=============================================================================
\section{Description of the environment used}
\label{sec:environment}
%=============================================================================

The application is a \textbf{client-side web application} rendering through \textbf{WebGL}, accessed via
the \textbf{three.js} library (r128) rather than through raw WebGL calls. The context is created by
\code{THREE.WebGLRenderer}, which selects WebGL\,2 when available and silently falls back to WebGL\,1; we
use no WebGL\,2-only feature, so both paths are correct. The renderer runs with \code{antialias:\,true}
(MSAA on the default framebuffer) and \code{powerPreference:\,'high-performance'} (asks for the discrete
GPU on dual-GPU laptops). The device pixel ratio is clamped with
\code{setPixelRatio(Math.min(devicePixelRatio,2))}: unclamped, a high-DPI display would quadruple the
fragment load for a barely perceptible gain. Output is written in sRGB
(\code{outputEncoding = THREE.sRGBEncoding}) so lighting is composited in linear space and converted once
at the end, which is what makes the emissive teals and pinks read correctly instead of washing out.

We chose three.js over hand-written WebGL deliberately: the intellectual content of the project is the
\emph{simulation} --- force laws, grid, octree, articulated model, gait --- and all of that is written from
scratch, so delegating context creation, shader compilation and matrix bookkeeping to a mature library let
us spend the available time on the parts that are actually ours. three.js is a rendering back end and a
scene-graph container here, never a simulation framework.

\paragraph{Language and execution model.} Plain \textbf{ES6+ JavaScript}: no TypeScript, no JSX, no
transpilation, no bundling, so the source that ships is the source that runs. The files are loaded as
\emph{classic scripts} (\code{<script src=\ldots>} in dependency order, one global lexical scope) rather
than ES modules --- a conscious trade-off, since browsers refuse to load modules over \code{file://}, which
would force every user to start a local server and would break the ``double-click \file{index.html}''
promise. Everything runs single-threaded inside the animation-frame callback; there are no Web Workers,
which bounds the achievable particle count (Section \ref{sec:limitations}).

\begin{center}
\small
\begin{tabular}{@{}ll@{}}
\toprule
\textbf{Requirement} & \textbf{Detail}\\
\midrule
Browser / GPU  & Any modern browser with WebGL (Chrome, Firefox, Edge, Safari); integrated graphics suffice\\
Network        & Needed \emph{once}, to fetch three.js from the CDN (\S\ref{sec:external})\\
Server / installation & Not required --- the \code{file://} protocol works; nothing to install\\

\end{center}

\noindent The layout is responsive: below 560\,px of viewport width the console expands to full width and
the HUD is hidden, and the camera accepts one-finger drag (orbit) and two-finger pinch (zoom). Piloting
and the drag tools need a keyboard and a mouse, so a desktop browser is the intended target.

\section{External libraries, tools and models}
\label{sec:external}
%=============================================================================

This section lists exhaustively everything in the delivered project that was \textbf{not} written by the
team.

\paragraph{Libraries.} \textbf{three.js r128}, loaded from \code{cdnjs.cloudflare.com} with a single
\code{<script>} tag, is the \emph{only} runtime dependency. It provides: the WebGL context and renderer
(\code{WebGLRenderer}); the scene graph (\code{Scene}, \code{Group}, \code{Object3D}) and its transform
composition; \code{PerspectiveCamera} and projection; the parametric geometry generators
(\code{SphereGeometry}, \code{CylinderGeometry}, \code{BoxGeometry}, \code{TorusGeometry},
\code{EdgesGeometry}); the standard PBR material (\code{MeshStandardMaterial}) and its shaders;
\code{InstancedMesh} for batched particle drawing; lights; \code{CanvasTexture}; \code{BufferGeometry} for
the line visualisations; and the math types (\code{Vector2/3}, \code{Color}, \code{Plane},
\code{Raycaster}).

That is the complete list. No UI framework (React, Vue), no control-panel library (dat.GUI, lil-gui,
Tweakpane), no physics engine (cannon.js, ammo.js), no math library (gl-matrix), no utility library
(lodash), no bundler (webpack, Vite, Rollup), no package manager, no CSS framework. The control console,
the matrix editor, the HUD and the camera controller were all written for this project; in particular we
did \emph{not} use three.js's own \code{OrbitControls}, because it ships as a separate add-on file and our
camera has to interoperate with the poke tools, which share the same mouse buttons.

\begin{notebox}{Models, meshes, animation and textures: none imported.}
There are no \code{.obj}/\code{.gltf}/\code{.fbx} files, no rigs, no keyframe data and no image files
anywhere in the project. Every piece of geometry is assembled at run time from three.js primitives:
particles are one \code{SphereGeometry(1,10,8)} drawn $N$ times by an \code{InstancedMesh}; the Grazer is
roughly two dozen spheres, cylinders and a torus composed into a hierarchy of \code{Group}s; the boundary
cage is an \code{EdgesGeometry} of a \code{BoxGeometry}; the octree, field and lattice visualisations are
\code{BufferGeometry} objects whose vertex buffers we fill by hand every frame. The walk cycle is not an
imported clip but a closed-form function of a phase accumulator (\S\ref{sec:gait}). All three texture maps
are painted procedurally into off-screen canvases at start-up and uploaded via \code{CanvasTexture}
(\S\ref{sec:textures}).
\end{notebox}

\paragraph{Fonts.} The CSS font stacks name Inter, SF Mono, JetBrains Mono and Roboto Mono, but no font is
\emph{fetched}: there is no \code{@font-face} rule and no Google Fonts link, and every stack ends in a
generic family (\code{system-ui}, \code{sans-serif}, \code{monospace}). The named fonts are used only if
the user's machine already has them, so the application carries no font dependency.

\paragraph{Conceptual credits.} The short-range rule model is our own implementation of the well-known
\emph{particle life} / ``Clusters'' idea popularised by Jeffrey Ventrella \cite{ventrella}, credited in the
application footer. No code was taken: the original demonstrations are 2D, use all-pairs evaluation and
have neither variable mass nor gravity. Our contribution is the extension to 3D, the mass-dependent
long-range term with a Barnes--Hut octree, the uniform-grid acceleration of the short-range term, the live
visualisations and the piloted creature. Barnes--Hut is the standard published method \cite{barneshut};
the implementation in \file{js/octree.js} is ours.

\paragraph{Development tools.} A text editor (source), the browser developer tools (debugging, profiling,
frame timing) and \LaTeX{} (this document). No compiler, bundler, package manager or asset pipeline is
part of the workflow.

\section{Software architecture}
\label{sec:architecture}
%=============================================================================

The project is deliberately flat: one HTML entry point, one stylesheet, ten JavaScript files, each with a
single responsibility.

\paragraph{Dependency order.} Because the files are classic scripts sharing one global scope, load order
\emph{is} part of the design; each file may use anything declared in the files before it. The order encoded
in \file{index.html} is exactly the dependency graph:
\code{config} $\to$ \code{scene} $\to$ \code{particles} $\to$ \code{creature} $\to$ \code{grid} $\to$
\code{octree} $\to$ \code{simulation} $\to$ \code{camera} $\to$ \code{ui} $\to$ \code{main}.
\file{config.js} is first because every other file reads \code{CFG}; \file{main.js} is last because it
bootstraps, and it is the only file that executes significant work at load time. The whole start-up
sequence is five lines:

\begin{lstlisting}
allocParticles(N); allocOctree(); rebuildGridDims(); randomizeMatrix(); seedParticles();
buildMesh(); buildCreature(); buildLattice(); buildPanel(); applyCam(); requestAnimationFrame(frame);
\end{lstlisting}

\paragraph{Data layout: structure of arrays.} Particles are \textbf{not} objects --- there is no
\code{Particle} class. State lives in parallel typed arrays (\code{px,py,pz}, \code{vx,vy,vz} as
\code{Float32Array}; \code{ptype} as \code{Uint8Array}; \code{psize}, \code{pmass} as \code{Float32Array}).
This is the single most important performance decision in the project, for three reasons. \emph{Cache
locality}: the inner loop streams sequentially through the position arrays instead of chasing pointers into
a scattered heap. \emph{No GC pressure}: the arrays are allocated once, at start-up or on a population
change, so in steady state the simulation allocates \emph{nothing} per frame and no collection pause ever
interrupts the animation. \emph{Predictable types}: \code{Float32Array} elements cannot be boxed, which
lets the JIT emit unboxed floating-point code for the whole loop. The same discipline is applied to the
octree (\S\ref{sec:octree}), a pooled structure of thirteen typed arrays rather than a tree of node
objects, and to the gravity-field samples.

\section{Technical aspects}
\label{sec:technical}
%=============================================================================

\subsection{Scene, lighting and procedural textures}
\label{sec:textures}

The scene is a dark volume with exponential fog (\code{FogExp2}, density $0.006$) matching the background
$\mathtt{0x05070d}$, so distant particles dissolve instead of ending abruptly at the far plane --- a cheap
depth cue in a scene that is otherwise a cloud of similar spheres. The camera is a
\code{PerspectiveCamera} ($55^\circ$ FOV, near/far $0.5$/$2000$) and is never manipulated directly: it is a
dependent variable of the orbit state (\S\ref{sec:orbit}). The rig is conventional --- a cool ambient fill,
a directional key and a directional rim that separates silhouettes --- plus two accent point lights with
finite range and quadratic decay, a teal one animated on a slow circle of radius 40 and a static pink one.
The moving teal highlight sweeping across a static clump is often the clearest signal that a structure is
three-dimensional rather than a flat sprite cloud; the accent pair can be toggled off.

Three $128\times128$ maps are painted into off-screen canvases at start-up: an \textbf{albedo} map (radial
gradient plus 900 faint speckles, kept deliberately \emph{light} because the per-instance colour multiplies
it and a dark albedo would mute the type colours); a \textbf{normal} map (neutral $(128,128,255)$ overlaid
with 70 radial gradients whose red and green channels are randomly offset, each blob a small bump, applied
at \code{normalScale} $(0.6,0.6)$ on particles and a subtler $(0.25,0.25)$ on the creature); and a
\textbf{roughness} map (mid-grey with 1400 random $2\times2$ squares, so a clump of identically-coloured
particles does not look like one moulded object). Total cost is a few milliseconds, once.

\subsection{Particle representation and instanced rendering}

Each particle has position, velocity, a type $t_i\in\{0,\dots,T-1\}$, a radius $s_i$ and a mass
$m_i=s_i^3$. Radii are drawn from a distribution deliberately skewed toward small values,
$s_i = s_0\big[(1-\mathit{sv}) + \mathit{sv}\,(0.4 + 3.4\,u^{2.2})\big]$ with $u$ uniform on $[0,1]$: the
exponent $2.2$ biases the variate toward zero, so the population is mostly small particles with a few large
ones which, because $m_i=s_i^3$, carry disproportionate gravitational mass: a handful of heavy seeds act as
attractors around which the light majority organises, exactly as in the astrophysical case being evoked.
Initial positions are uniform \emph{by volume} inside a
sphere, which requires the cube-root inversion of the radial CDF (\code{r = Math.cbrt(Math.random())*R});
omitting the \code{cbrt} would concentrate particles near the centre and seed a gravitational collapse
before the user has touched anything.

All $N$ particles are drawn by a single \code{InstancedMesh}: one geometry, one material, one draw call.
The instance matrix buffer is flagged \code{DynamicDrawUsage}, and per-instance colour is written only on a
type change via \code{setColorAt}, so only the transform buffer is re-uploaded each frame:

\code{syncMesh()} rewrites the $N$ matrices each frame using a single reused
\code{Object3D} as a scratch composer, so it allocates nothing. The
sphere is only $10\times8$ segments (80 faces): at $N=3000$ that is a quarter of a million triangles, which
is comfortable, whereas $32\times16$ would be a million, which is not. The normal map restores the surface
detail the coarse tessellation gives up.

\subsection{Short-range chemistry and the uniform grid}
\label{sec:chem}

With $\hat r = r/r_{\max}$, $\beta$ the repulsion-core fraction and $a=A_{t_it_j}$ the signed matrix entry,
the scalar force profile is piecewise linear:

\begin{equation}
F(\hat r, a) =
\begin{cases}
\dfrac{\hat r}{\beta} - 1, & 0 \le \hat r < \beta \quad\text{(universal repulsion)}\\[6pt]
a\left(1 - \dfrac{\big|\,2\hat r - 1 - \beta\,\big|}{1-\beta}\right), & \beta \le \hat r < 1 \quad\text{(typed interaction)}\\[6pt]
0, & \hat r \ge 1
\end{cases}
\end{equation}

Three properties carry the whole design. \textbf{The repulsion core is universal}: below $\beta$ the
profile does not depend on $a$, so every particle pushes every other away at close range regardless of
type, preventing total collapse under mutual attraction --- the $\beta$ slider is effectively an
incompressibility control. \textbf{The interaction is compactly supported}: $F$ is exactly zero beyond
$r_{\max}$, not asymptotically small, which is the precondition for the grid below. \textbf{The matrix is
asymmetric}: $A_{ij}$ and $A_{ji}$ are independent, so Newton's third law is deliberately violated and a
pair in which red chases green while green flees red self-propels. Physically false, behaviourally
essential: it is the source of every chasing and locomotive pattern in the system. The acceleration is

\begin{equation}
\mathbf{a}_i^{\text{chem}} = r_{\max}\,k \!\!\sum_{j \,:\, r_{ij} < r_{\max}} \!\! F\!\left(\frac{r_{ij}}{r_{\max}},\, A_{t_i t_j}\right) \hat{\mathbf{d}}_{ij},
\end{equation}

\noindent with $k$ the \code{forceStrength} slider. The $r_{\max}$ factor keeps the effective force scale
roughly constant as the user drags the interaction radius, so changing $r_{\max}$ changes the
\emph{geometry} of the patterns rather than simply making everything more violent.

\paragraph{Uniform grid.} Since the kernel has compact support, particles are binned into a grid of cell
size $r_{\max}$ (resolution capped at $64^3$ cells) and only the 27 neighbouring cells are searched --- a
\emph{complete} search domain, not an approximation. The grid is rebuilt from scratch every frame by a
three-pass counting sort into flat typed arrays, which allocates nothing:

\begin{lstlisting}
function buildGrid(){
  cellCount.fill(0);
  for(let i=0;i<N;i++){ const c=cellIndex(px[i],py[i],pz[i]); cellOf[i]=c; cellCount[c]++; }
  let acc=0;
  for(let c=0;c<gCells;c++){ cellStart[c]=acc; acc+=cellCount[c]; }
  cellStart[gCells]=acc;
  const cursor=cellStart.slice(0,gCells);
  for(let i=0;i<N;i++){ const c=cellOf[i]; sortedIdx[cursor[c]++]=i; }
}
\end{lstlisting}

\noindent Pass 1 histograms the cells, pass 2 turns the histogram into a prefix sum, pass 3 scatters
indices so that the members of cell $c$ occupy one contiguous slice of \code{sortedIdx}. The build is
$O(N+\text{cells})$ and the layout it produces means the inner loop walks neighbours contiguously in
memory. With roughly constant density the expected query cost is $O(N)$: at $N=3000$, the difference
between $9\times10^6$ pair tests per frame and a few tens of thousands.

\subsection{Long-range gravity: Barnes--Hut octree}
\label{sec:octree}

Gravity has infinite support, so the grid trick does not apply and exact evaluation is irreducibly
$O(N^2)$. We use the Barnes--Hut approximation \cite{barneshut}: a distant \emph{group} of particles is
replaced by a single pseudo-particle at its centre of mass. The tree is a pooled structure of thirteen
typed arrays indexed by node id --- centre \code{nCx/nCy/nCz}, half-width \code{nHalf}, mass \code{nMass},
centre of mass \code{nComX/Y/Z}, \code{nBody} (body index if leaf, $-1$ otherwise), \code{nInternal},
\code{nDepth} and \code{nChild} ($8$ ids per node) --- sized once at $\max(256, 4N+64)$ nodes on a
population change. Rebuilding every frame then costs \emph{zero} allocations: \code{buildOctree()} resets
\code{nodeCount=0} and re-uses the pool, and children are created lazily so empty space costs nothing.

Bodies are inserted one at a time into a root cube covering the world. The insertion loop handles the
standard subtle case: inserting into an occupied leaf requires pushing the existing body down too, and if
both bodies land in the same octant the process must recurse.

\begin{lstlisting}
if(nInternal[node]===0){
  if(nBody[node]===-1){ nBody[node]=i; return; }             // empty leaf: done
  const e=nBody[node]; nBody[node]=-1; nInternal[node]=1;    // occupied: subdivide
  if(nHalf[node]<0.02) return;                               // coincident-body guard
  const ce=childOf(node, octant(node,px[e],py[e],pz[e])); nBody[ce]=e;
  const ci=childOf(node, octant(node,px[i],py[i],pz[i]));
  if(ci===ce){ node=ci; continue; }                          // same octant: go deeper
  nBody[ci]=i; return;
}
\end{lstlisting}

\noindent The \code{nHalf < 0.02} guard is essential: two coincident bodies would otherwise subdivide
forever and hang the browser. Below that cell size the body is dropped from the tree for that frame --- an
invisible error at this scale, and a hard bound on depth; a second guard caps the loop at 64 iterations. A
post-order recursion then aggregates $M_{\text{node}}=\sum_c M_c$ and
$\mathbf{X}_{\text{node}}=M_{\text{node}}^{-1}\sum_c M_c\mathbf{X}_c$.

For each particle the tree is walked with an explicit stack (a reused \code{Int32Array(4096)}: recursion
would mean a JS call frame per node and no way to bound depth). A node of width $s$ at distance $d$ is
accepted as a single pseudo-particle when $s/d<\theta$, evaluated in squared form
(\code{if(s*s < theta2*d2)}) to avoid a square root per test, and is otherwise opened. The contribution of
an accepted node is the softened inverse-square law

\begin{equation}
\mathbf{a}_i \mathrel{+}= \frac{G\,M_{\text{node}}\,(\mathbf{X}_{\text{node}} - \mathbf{x}_i)}{\left(\|\mathbf{X}_{\text{node}} - \mathbf{x}_i\|^2 + \varepsilon^2\right)^{3/2}}.
\end{equation}

\noindent Softening is not cosmetic: without it two particles passing close together produce
$\|\mathbf{a}\|\propto 1/r^2\to\infty$ and, with a finite time step, are slingshotted to infinity. The
$\varepsilon^2$ term bounds the force at $GM/\varepsilon^2$; as in the standard formulation it enters the
force but not the opening test. $\theta$ is exposed as a slider because it \emph{is} the algorithm's
central dial: $\theta\to0$ opens every node and degenerates to exact $O(N^2)$; $0.5$ is accurate and slow;
$0.8$ is the default $O(N\log N)$ compromise; $1.6$ is fastest, with visible clumping artefacts. The HUD's
node count makes the trade-off legible in real time. A second entry point, \code{gravityAccelAt()},
evaluates the same field at an arbitrary point --- identical but without the self-exclusion test --- and
drives the field and lattice visualisations.

\subsection{Integration, stability and boundaries}

The two force terms, plus the creature field and the user's intervention field, are summed per particle and
integrated with \textbf{semi-implicit (symplectic) Euler} --- velocity first, then position from the
\emph{new} velocity, which is markedly more stable for orbital motion than explicit Euler at the same cost.
Friction is an exponential decay expressed through a \emph{half-life},
$\mu = 2^{-\Delta t/T_{1/2}}$, $\mathbf{v}\leftarrow\mu\mathbf{v}+\mathbf{a}\Delta t$: framerate-independent
by construction, and a control with a physical meaning (``motion halves in this long'') instead of an
arbitrary coefficient. Three further measures keep the system alive: a \textbf{time-step clamp}
(\code{simulate(1/60*Math.min(2, rdt*60))}, with the raw frame delta itself clamped at 50\,ms) so that
returning from a background tab costs a moment of slow motion instead of an explosion; a \textbf{velocity
clamp} at 90 units/s as a last line of defence; and a \textbf{two-pass update}, in which forces for
\emph{all} particles are computed from start-of-step positions before \emph{any} position is written --- a
single fused loop would let particle $j$ see particle $i$'s updated position, making the result depend on
particle numbering.

Two boundary modes are toggled live. \textbf{Reflecting walls} (default) clamp positions to the cube and
reverse the normal velocity with restitution $0.6$. \textbf{Toroidal wrap} makes space a 3-torus, which is
more than a position remap: the \emph{forces} must wrap too or structures would tear at the seams. The
short-range term therefore uses the minimum-image convention (a separation longer than half the box is
replaced by the shorter way round) and the 27-cell sweep wraps modulo \code{gN} --- enabled only when
$\mathtt{gN}\ge3$, below which a cell would be its own neighbour twice and pairs would be double-counted.
The position remap uses a floor rather than a conditional subtraction
(\code{px[i] -= worldW*Math.floor((px[i]+h)/worldW)}) so that a particle overshooting by more than one box
width still lands correctly instead of flickering at the edge. Gravity is deliberately \emph{not} wrapped:
a periodic gravitational field needs an Ewald summation, far beyond a real-time browser demo, so under wrap
it is a documented approximation.

\subsection{The Grazer: hierarchical modelling and procedural gait}
\label{sec:creature}
\label{sec:gait}

The creature demonstrates the classical hierarchical-modelling requirement: a tree of transforms in which
each child's world transform is the composition of its own local transform with all of its ancestors'. We
use three.js's scene graph as the transform tree, but the hierarchy, the joint layout and the motion are
ours. Depth from root to foot is five levels:

\begin{center}
\small\ttfamily
root \textrm{(Group)} $\to$ \{ body+belly \textbar{} face $\to$ eye $\to$ (sclera, pupil, glints)
\textbar{} antenna$\times$2 $\to$ (stalk, bulb) \textbar{} hip$\times$4 $\to$ thighPivot $\to$ knee $\to$
shinPivot $\to$ foot \}
\end{center}

\noindent Rotating \code{thighPivot} carries the knee, shin and foot with it; rotating \code{shinPivot}
carries only the foot. The subtlety in building an articulated limb from primitives is that a
\code{CylinderGeometry} is generated centred on the origin and aligned with $+y$, which is the wrong frame
for a bone --- rotating such a mesh about a joint would swing it about its middle. The geometry is
therefore baked into the correct frame once, at build time:

\begin{lstlisting}
const thighGeo = new THREE.CylinderGeometry(0.2, 0.16, L1, 10);
thighGeo.rotateZ(-Math.PI/2);     // lie along +x instead of +y
thighGeo.translate(L1/2, 0, 0);   // span 0..L1, so the joint sits at the origin
const knee = new THREE.Group(); knee.position.set(L1,0,0); thighPivot.add(knee);
\end{lstlisting}

\noindent Because the knee is a \emph{child} of the thigh's pivot it inherits every rotation of the thigh
automatically: the segments cannot come apart, not because the animation is careful but because the
hierarchy makes separation unrepresentable. The four hips sit on the body surface at radius $2.45$ and are
rotated so each limb's local $+x$ points radially outward, so thighs sweep away from the body and never
intersect it.

The walk cycle is a closed-form function of a phase accumulator --- there is no keyframe data anywhere:

\begin{lstlisting}
const gaitSpeed = 5 + moving*0.5;      // legs cycle faster when moving faster
c.phase += dt*gaitSpeed;
for(const leg of c.legs){
  const ph = c.phase + leg.phase;              // per-leg constant offset 2*pi*k/4
  const lift = Math.max(0, Math.sin(ph)), swing = Math.cos(ph);
  leg.thighPivot.rotation.z = 0.18 + swing*0.24 - lift*0.10;
  leg.thighPivot.rotation.y = swing*0.16;
  leg.shinPivot.rotation.z  = -1.7 + lift*0.5;
}
\end{lstlisting}

\noindent The four constant phase offsets $2\pi k/4$ distribute the legs evenly around the cycle so the
gait reads as a coordinated walk rather than four independent twitches. The half-wave rectification
$\max(0,\sin)$ distinguishes the two halves of the cycle: during swing the leg lifts, during stance
\code{lift} is pinned to zero so the foot stays planted --- a lift term of $\sin$ alone would make the leg
burrow into the ground on the downstroke. The constant $-1.7$\,rad of knee bend gives the silhouette its
insect-like character. Three secondary motions layer on top, all closed-form: a hover bob $\sin(2.2t)$ on
the root, springy antennae leaning back in proportion to speed, and a stochastic blink that squashes the
eye's $y$ scale for 140\,ms then re-arms after $2.5$--$5$\,s. Heading is critically damped rather than
snapped (\code{rotation.y += (heading-rotation.y)*min(1,dt*6)}), so turns ease instead of popping.

\paragraph{A solid body with a field.} The Grazer is not a ghost. After integration, particles inside its
bounding radius are projected onto the surface and given an outward impulse $-1.4\,v_n$, leaving a residual
$-0.4\,v_n$ (restitution $0.4$); the impulse is applied only when $v_n<0$, i.e.\ only to particles moving
\emph{into} the surface, without which a particle sliding along it would be kicked repeatedly. The proxy is
a sphere rather than the visual mesh --- per-triangle collision against an articulated body would cost more
than the rest of the frame for an imperceptible difference. Within a radius $R$ the creature also applies a
quadratic-falloff radial force plus a tangential swirl,

\begin{equation}
\mathbf{a} \mathrel{+}= \underbrace{\sigma\,S\,\frac{(1-d/R)^2}{d}\,\mathbf{d}}_{\text{attract/repel}}
\;+\;
\underbrace{0.25\,S\,\frac{(1-d/R)}{d}\,(-d_z,\,0,\,d_x)}_{\text{swirl about }y},
\end{equation}

\noindent with $\sigma=\pm1$ the mode and $S$ the strength slider. The quadratic falloff makes the field
vanish smoothly at $r=R$ instead of cutting off with a discontinuity visible as a hard shell, and the swirl
term is why gathered particles orbit the creature instead of piling into a static ball --- it converts pure
radial infall into an accretion disc, which is far more legible as motion. The aura sphere is scaled to
exactly $R$, so the visible bubble is an honest depiction of the field's reach, and its colour tracks the
mode (cool blue for attract, warm orange for repel).

\subsection{Visualising the invisible}
\label{sec:viz}

\textbf{Octree wireframe.} A recursive walk emits the twelve edges of each occupied node's cube into a
\code{BufferGeometry}, capped at depth 6 and skipping empty leaves. The result makes Barnes--Hut adaptivity
immediately obvious: cells are large in empty space and subdivide finely exactly where mass concentrates.

\textbf{Gravitational field streamlines.} The field is sampled on an $n\times n\times n$ lattice
($n=\code{fieldN}$, up to $20^3=8000$ samples) via \code{gravityAccelAt}. Each sample is drawn as two
segments sharing one geometry: a faint full-length vector showing structure, and a bright pulse travelling
along it toward mass, parameterised by \code{f = ((t*speed + FLD.ph[k]) \% 1 + 1) \% 1} with a glow
$0.45+0.55\sin(\pi f)$. The per-sample phase \code{FLD.ph[k]} is the linear function
$0.05x+0.045y+0.04z$ of position: because the coefficients are unequal the wave sweeps diagonally across the
volume and never resynchronises into a distracting pulse-in-unison. Colour interpolates teal $\to$ orange
with strength, magnitudes are normalised against the frame maximum, and samples below $4\%$ collapse to a
degenerate point rather than being culled, keeping the vertex count constant so the buffer is never
reallocated. Rendering is additive with \code{depthWrite:false}. Crucially, the sample \emph{directions} are
rebuilt only every fourth frame while the pulse is redrawn every frame: the expensive part (8000 octree
traversals) runs at 15\,Hz, the cheap part at 60\,Hz, and the eye cannot tell.

\textbf{Deforming space lattice.} A $9^3$ grid of nodes joined by $\sim1944$ segments is displaced from its
rest position by the local gravitational acceleration ($\times7$) and by the user's active poke field,
capped at 9 units so a violent warp bends space instead of shredding the lattice. Rest positions are stored
separately from current ones, so the deformation is always computed from the undeformed state and never
accumulates drift. It is the intended companion to the Warp tool.

\subsection{The frame loop and performance}
\label{sec:perf}

\begin{lstlisting}
function frame(now){
  const rdt = Math.min(0.05, (now-last)/1000); last=now;   let octRoot = -1;
  if(CFG.running) octRoot = simulate(1/60*Math.min(2, rdt*60));   // physics
  pilot(rdt); animateCreature(rdt, t); syncMesh();                // input, gait, instances
  if((CFG.showField||CFG.showLattice) && CFG.gravity && octRoot<0) octRoot = buildOctree();
  if(CFG.follow && creature.root) cam.target.lerp(creature.root.position, 0.05);
  applyCam(); renderer.render(scene, camera); requestAnimationFrame(frame);
}
\end{lstlisting}

\noindent \code{simulate()} \emph{returns} the octree root it built so the visualisations reuse it; the
tree is constructed independently only when the simulation is paused but a visualisation still needs it.
The follow camera uses \code{lerp(\ldots,0.05)} rather than assignment, giving a damped chase that lags
slightly --- an instant snap would make the whole world jitter with the gait's hover bob.

%=============================================================================
\section{Implemented interactions}
\label{sec:interactions}
%=============================================================================

The application is interactive in five registers: the user can \emph{look} (camera), \emph{touch} (drag
tools), \emph{strike} (one-shot impulses), \emph{inhabit} (piloting the creature) and \emph{legislate}
(editing the rules).

\subsection{Camera control}
\label{sec:orbit}

The camera is driven by a hand-written spherical orbit state
(\code{\{target, theta, phi, radius\}}), from which the position is recomputed each frame and pointed at
the target. Left-drag orbits ($\theta \mathrel{-}= 0.005\Delta x$, $\phi \mathrel{-}= 0.005\Delta y$) when
the Orbit tool is active; right-drag orbits \emph{always}, whatever tool is selected, so the user is never
trapped in a tool (the canvas context menu is suppressed to make this possible); middle-drag or
\keys{Shift}+left-drag pans; the wheel zooms; touch gives one-finger orbit and two-finger pinch. Four
details matter: $\phi$ is clamped to $[0.08,\pi-0.08]$, because reaching a pole exactly makes the view
direction parallel to the up vector and \code{lookAt} produces a degenerate basis that flips the camera;
zoom is \emph{multiplicative} ($\times1.08$ per notch, clamped to $[20,500]$), since an additive zoom crawls
when far away and overshoots through the subject when close; pan speed scales with radius so a given mouse
movement always covers the same fraction of the screen; and panning silently cancels follow mode, without
which the camera would fight the user's input and lose --- which reads as a bug rather than a feature.

\subsection{Direct manipulation: the drag tools}

Four tools share the left mouse button: \textbf{Orbit} (default, no effect on the simulation),
\textbf{Push} (radial outward force inside the brush sphere, blasting a cavity in the soup), \textbf{Pull}
(radial inward, gathering particles into the cursor) and \textbf{Warp} (a violent composite of swirl,
collapse and axial compression producing a lensing/folding effect). The brush radius is a slider (5--60
units) and a master \textbf{Intensity} multiplier (0.2--6$\times$) scales the tools \emph{and} every impulse
below. A translucent sphere with a rotating ring marks the brush in the scene, sized to $R$ and coloured by
mode, so the region of influence is never guesswork.

The mouse gives a 2D position but the force needs a 3D one, so \code{screenToWorld()} converts pixels to
NDC, builds a ray with \code{Raycaster.setFromCamera} and intersects it with the plane through the orbit
target whose normal is the camera's view direction --- the plane the user perceives as ``the screen, pushed
into the scene''. Because that plane always faces the camera, the tool acts at the depth the user is
looking at and behaves identically from every angle; the function reuses five module-level scratch objects
and allocates nothing, which matters because it runs on every \code{mousemove}. With $d$ the distance to the poke centre, $R$ the brush radius,
$\text{fall}=1-d/R$ and $I$ the intensity:

\begin{align}
\text{Push/Pull:}\quad & \mathbf{a} \mathrel{+}= \pm\,420\,I\,\frac{\text{fall}^2}{d}\,\mathbf{d}\\[2pt]
\text{Warp:}\quad & \mathbf{a} \mathrel{+}= \underbrace{620\,I\,\text{fall}^2\,(\hat{\mathbf{n}} \times \mathbf{d})}_{\text{swirl}}
   \;\underbrace{-\;520\,I\,\frac{\text{fall}^2}{d}\,\mathbf{d}}_{\text{collapse}}
   \;\underbrace{-\;300\,I\,\text{fall}\,(\mathbf{d}\cdot\hat{\mathbf{n}})\,\hat{\mathbf{n}}}_{\text{axial compression}}
\end{align}

\noindent The swirl axis $\hat{\mathbf{n}}$ is captured as the camera's forward vector at the moment the
drag begins, so the vortex always spins in the plane of the screen and the user sees a whirlpool face-on
rather than edge-on. The quadratic falloff again avoids a hard edge at $r=R$.

\subsection{One-shot impulses}

Six buttons apply an instantaneous change to every particle, centred on the current orbit target --- i.e.\
on whatever the user is looking at. Unlike the drag tools they modify velocity (or, for Fold, position)
directly rather than adding a force. \textbf{Shockwave}: radial outward kick $40I/(1+0.05d)$, an explosion
decaying with distance. \textbf{Implode}: radial inward, $45I/(1+0.04d)$. \textbf{Vortex}: tangential kick
$35I$ about the vertical axis through the epicentre, plus a small random vertical component that keeps the
disc from becoming perfectly flat. \textbf{Warp}: swirl about the view axis plus inward collapse, both
$\propto1/(1+0.03d)$. \textbf{Jitter}: a uniform random kick up to $40I$ per axis --- thermal noise, useful
for shaking a structure out of a local minimum. \textbf{Fold} is the most interesting, because it is a
transformation of space rather than a force: with $\hat{\mathbf{n}}$ the view axis, every particle on the
far side of the plane is mirrored onto the near side, \emph{position and velocity}:

\begin{lstlisting}
if(along>0){
  px[i]-=2*along*ax; py[i]-=2*along*ay; pz[i]-=2*along*az;   // mirror position
  const vn = vx[i]*ax + vy[i]*ay + vz[i]*az;
  vx[i]-=2*vn*ax; vy[i]-=2*vn*ay; vz[i]-=2*vn*az;            // mirror velocity
}
\end{lstlisting}

\noindent Reflecting the velocity as well as the position is what makes the result coherent: a mirrored
particle continues along the mirrored trajectory, so folding a rotating galaxy produces two
counter-rotating halves that then collide, rather than a pile of particles moving incoherently.

\subsection{Piloting the Grazer}

\keys{W}/\keys{S} move forward/backward along the creature's heading; \keys{A}/\keys{D} strafe \emph{and}
turn the heading ($\pm1.8$\,rad/s); \keys{Q}/\keys{E} ascend/descend; \keys{Shift} boosts acceleration
$2.2\times$; \keys{H} shows or hides the console. Movement is force-based rather than positional: the input
assembles an acceleration in the creature's local frame, which is integrated with heavy exponential
damping.

\begin{lstlisting}
if(active) accel.normalize().multiplyScalar(60*boost);   // normalize: no faster diagonals
c.vel.addScaledVector(accel, dt);
c.vel.multiplyScalar(Math.pow(0.02, dt));                // damping, framerate-independent
c.root.position.addScaledVector(c.vel, dt); c.root.position.clamp(min, max);
\end{lstlisting}

\noindent The \code{normalize()} before scaling is what stops diagonal movement from being $\sqrt2$ times
faster than axis-aligned movement --- the classic bug --- and the damping uses the same
framerate-independent exponential form as the particle friction. The result has weight: the creature
accelerates and coasts rather than teleporting, which also means it stirs the soup as it goes. A hint bar
listing the controls fades in while the creature moves and out when it stops, so the controls are
discoverable without a permanent overlay. A \textbf{Follow camera} toggle makes \code{cam.target} chase the
creature with a $5\%$ lerp per frame; as noted, panning cancels it.

\subsection{Editing the rules: the attraction matrix}

The most consequential interaction is also the smallest widget. The editor is a $T\times T$ grid of
coloured cells with row and column headers of type swatches; \textbf{rows act on columns}, so cell $(i,j)$
is the force type $i$ feels toward type $j$. Colour encodes value (green attraction, red repulsion,
near-black neutral, intensity $\propto|A_{ij}|$); clicking a cell cycles it through
$+1\to+0.5\to0\to-0.5\to-1\to+1$, snapping to the nearest step first so a cell holding a random value like
$0.37$ from \emph{Reroll} still cycles sensibly; a tooltip reports the exact value
(\code{type 2 -> 3 (-0.50)}); and changes are instantaneous, because \code{A} is read directly by the force
kernel every frame --- no apply button, no reseed. The asymmetry is the pedagogical point and the editor is
built to make it discoverable: setting $A_{01}=+1$ and $A_{10}=-1$, one click each, makes type 0 chase type
1 while type 1 flees, and the pair immediately begins to self-propel across the volume; making the matrix
symmetric instead produces static clumps. A user can find this out in ten seconds without reading anything.

\subsection{The control console and presets}

The console is a collapsible panel of nine groups, all collapsed by default so the interface is not a wall
of sliders, and every control carries a one-line explanation underneath it. It is built by a small widget
factory (\code{slider}, \code{toggle}, \code{btn}, \code{group}, \code{withDesc}) --- around 30 lines of DOM
code that replaces a UI dependency.

\paragraph{Live reconfiguration.} Several controls rebuild live state, which is where the interesting
engineering hides. \emph{Particle count} reallocates all nine typed arrays, the octree pool and the grid,
then reseeds and rebuilds the \code{InstancedMesh} (whose instance count is fixed at construction); it is
bound to \code{change} rather than \code{input}, so it fires once on release instead of on every pixel of
the drag. \emph{Interaction radius} changes the grid cell size, so \code{rebuildGridDims()} runs on every
step --- cheap, since only index arrays are reallocated. \emph{World size} is the subtlest: rather than
clipping particles into the new volume it \emph{scales all positions} by the ratio of new to old half-width,
so structures survive the resize instead of being crushed against the walls.

\paragraph{Presets.} Nine presets reconfigure rules, gravity and size distribution in one click, each a
genuinely different regime: \textbf{Cells} (5 types, no gravity, $r_{\max}=10$ --- soft membrane-like blobs),

spiral orbiting clumps), \textbf{Web} (6, none, 9 --- connected filament network), \textbf{Orbits} (3,
$G=2.4$, 6 --- slow stable orbits), \textbf{Worms} (3, none, 14 --- wriggling chains), \textbf{Crystal} (4,
none, 8 --- rigid lattice-like solid), \textbf{Nebula} (5, $G=0.7$, 11 --- diffuse swirling clouds) and
\textbf{Swarm} (3, none, 13 --- flocking drift). Each also sets $\beta$, the friction half-life and the size
variance, rerolls the matrix, reseeds and rebuilds the panel. Because the matrix is rerolled, clicking the
same preset twice gives two different worlds \emph{of the same character}: the preset fixes the regime, not
the outcome.

\section{Limitations, future work and conclusions}
\label{sec:limitations}
%=============================================================================

Each limitation below is a considered trade-off rather than an oversight. The simulation is
\textbf{single-threaded and CPU-bound}: beyond roughly 3000 particles the force evaluation, not the
rendering, is the bottleneck, and the fixes --- a Web Worker with a \code{SharedArrayBuffer}, which needs
COOP/COEP headers and therefore a server, or GPU-side integration --- would either break the \code{file://}
promise or require a substantial rewrite. \textbf{Gravity is not periodic}: under \emph{Wrap edges} the
short-range term uses the minimum image but gravity still sees the non-wrapped configuration, since a
correct treatment needs an Ewald summation. \textbf{The creature's collision proxy is a sphere}, so
particles bounce off an invisible ball rather than off the legs, and \textbf{the gait is not foot-locked},
so a slight skate remains at high speed --- proper foot-locking needs inverse kinematics.
\textbf{Momentum is not conserved}, by design: the asymmetric matrix violates Newton's third law, which is
the entire point of the chemistry model but does mean there is no conserved quantity to validate against.
\textbf{Bodies are dropped at extreme density} by the octree's coincident-body guard, a small bounded error
preferable to an infinite subdivision that would hang the browser, and \textbf{instance count is fixed at
construction}, so changing the particle count rebuilds the \code{InstancedMesh} --- which is why that
control fires on slider release. Natural extensions: GPU-side integration; an IK solver with foot locking;
multiple creatures flocking among themselves; saving matrices as shareable URLs; and soft-body chains built
on the existing neighbour grid.

\medskip
\noindent \textsc{Primordia} sets out to demonstrate that complexity does not require complicated rules.
Two force laws --- a piecewise-linear typed kernel and a softened inverse-square law --- acting at two
different spatial scales are enough to produce cells, chains, filaments, orbits, spirals and swarms, none of
which appears anywhere in the source as an explicit construct. What makes this interactive rather than
merely correct is the pairing of each law with the acceleration structure suited to its scale: a uniform
grid, valid precisely because the short-range kernel has compact support, and a Barnes--Hut octree, valid
because a distant cluster is well approximated by its centre of mass. Both are built on pooled typed arrays,
so the steady-state allocation rate is zero. The user-facing payoff of that work is the $\theta$ slider and
the octree visualisation: the approximation is not hidden behind the curtain, it is on stage. The project
also meets its asset-free constraint completely --- every vertex, texel and joint angle is computed at run
time, and the whole application is one HTML file, one stylesheet and ten JavaScript files with a single
third-party dependency.
